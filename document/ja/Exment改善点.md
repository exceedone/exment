# Exment 改善点・課題整理
最終更新日: 2026-04-03

## 1. UI/UXに関する課題
### 1.1 全体的な直感性の不足
Exmentは機能が幅広く揃っている一方、初見ユーザーが機能の配置を理解するまでに時間がかかる場面がある。

課題:
- 画面ごとの役割が把握しにくい
- 設定対象（テーブル/ビュー/フォーム）の違いが伝わりにくい

### 1.2 テーブル一覧へのアクセス性
現状、一般ユーザーが「アクセス可能なテーブル全体」を横断一覧しやすい導線は弱い。  
`CustomTable` 画面は設定・管理用途が中心で、一般利用の導線とは役割が異なる。

補足:
- テーブル管理系は管理ルート配下（`table` リソース）で運用される
- 一般利用は主にメニュー構成や `data/{tableKey}` 導線に依存する

改善案:
- ユーザー向け「利用可能テーブル一覧」ページを標準提供
- 権限に応じて表示対象を自動フィルタ
- 初期ナビゲーションに「データ一覧（全体）」を配置可能にする

### 1.3 カスタム列設定の一括操作性
カスタム列設定において、検索インデックスなどの項目を列ごとに個別設定する必要があり、管理コストが高くなりやすい。

課題:
- 同種の列設定を何度も繰り返す必要がある
- 列数が増えると設定漏れや設定ブレが起きやすい

改善案:
- 複数列を選択して検索インデックス等を一括更新できるUIを提供
- 既存列設定のコピー適用（テンプレート化）を可能にする
- 変更対象列のプレビューと差分確認を実装し、誤更新を防ぐ

### 1.4 カスタムビュー設定時の画面遷移負荷
カスタムビュー設定のたびに別ページへ遷移するため、試行錯誤のテンポが落ち、操作が直感的になりにくい。

課題:
- 条件変更と結果確認の往復に手間がかかる
- 初学者にとって設定反映の流れが分かりにくい

改善案:
- 一覧画面上でドロップダウン/サイドバーからビュー条件を編集可能にする
- 設定変更時に一覧を即時更新（プレビュー）し、結果をその場で確認できるようにする
- 既存の詳細設定画面は「高度設定」として残し、用途を分離する

### 1.5 データ一覧での並び替え操作
並び替えのために新規ビュー作成が必要なケースがあり、日常的な一覧操作としては手数が多い。

課題:
- 一時的な並び替えにも設定作業が発生する
- フィルタに比べてソート操作の自由度が低い

改善案:
- フィルタと同様に、一覧画面で都度ソート条件を変更できるUIを提供
- 複数列ソート（優先順位付き）をその場で設定可能にする
- 必要な場合のみ現在のソート条件をビューとして保存できる導線を用意する

## 2. ダッシュボードUXの課題
現状のダッシュボードは、`target_table_id` と `target_view_id` を選んで表示する前提のため、ビュー事前作成が必要。

課題:
- ダッシュボード画面で試行錯誤しにくい
- 分析作業において、画面遷移が多くなる
- 内部構造（テーブル・ビュー）の理解をユーザーに要求しやすい

改善案:
- 全テーブル一覧の表示
- テーブル間関連の選択（JOINキー候補の提示）
- 集計条件の設定
- チャート生成までワンフロー化

イメージ:
1. 「売上テーブル」と「顧客テーブル」を選択
2. `customer_id` で関連付け
3. 地域別売上を集計
4. そのままグラフ化

## 3. カスタムビュー（JOIN機能）の制約
### 3.1 現状の整理
リレーション定義によるJOIN相当の処理は可能。  
ただし、SQL自由記述型の分析ビューではないため、複雑な分析クエリには限界がある。

実装上の確認:
- リレーションJOINを検索サービス層で実行
- サマリー関数は `SUM / COUNT / MIN / MAX` を提供（`AVG` は未有効）

### 3.2 想定される限界（難易度が上がるケース）
以下は「標準GUIだけでは難しくなる」可能性が高い。

例:
- 多段JOIN（案件 → 顧客 → 企業 → 地域 など3テーブル超）
- 複合集計（顧客別総売上 + 最新取引日を同時取得）
- JOIN条件に高度な条件式を含めるケース
- サブクエリ前提（最新1件、ランキング上位のみ等）

### 3.3 改善方向
- GUIベースのJOINエディタ強化（関連経路を視覚化）
- 集計関数拡張（AVG、比率、移動平均など）
- 仮想ビュー/派生テーブル機能（分析用データセット生成）
- 条件テンプレート（最新1件、Top-N、期間比較）を標準提供
